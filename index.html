Core Topic AP Lifecycle

AP Discovery & Join Flow: AOS 8 vs AOS 10

Tahapan booting access point hingga berhasil mendapatkan status UP dan melayani SSID.

1. Urutan Discovery Controller (Discovery Order Hierarchy)

  1. Static Environment: Variabel NVRAM tersimpan di AP (`master=<ip>`).
  2. DHCP Option 43: Vendor specific string berisi IP Controller.
  3. ADP (Aruba Discovery Protocol):
    • Multicast: Mengirim frame ke IP 239.0.82.11.
    • Broadcast: Mengirim paket ke port UDP 8211.
  4. DNS Resolution: Query default: aruba-master.<domain-name-dari-dhcp>.

2. Control Plane Security (CPsec) & Port Firewall

Setelah IP Controller ditemukan, komunikasi control-plane wajib melewati enkripsi IPsec (CPsec). Jika sertifikat/MAC AP belum disetujui (*Approved*), AP akan masuk status I (Inactive).

(MC-01) # show whitelist-db cpsec

1. Alur Zero Touch Provisioning (ZTP) Cloud

Pada AOS 10, tidak ada Mobility Master lokal. AP bertindak sebagai cloud-managed device dan berkomunikasi langsung ke Aruba Central menggunakan enkripsi WebSocket/TLS.

  1. DHCP Initialization: AP wajib menerima IP, Gateway, DNS Server, dan NTP time yang valid.
  2. Koneksi ke Aruba Activate: HTTPS GET ke activate.arubanetworks.com (Port 443).
  3. Mutual TLS via TPM Chip: Validasi sertifikat hardware pabrik yang tersimpan di chip TPM AP.
  4. Redirect ke Central Cluster: Activate merespons URL cluster Central tenant (contoh: app-ap1.central.arubanetworks.com).
  5. Firmware & Policy Sync: Central mengecek subscription license, upgrade OS ke image AOS 10, dan sync konfigurasi Group.

2. Titik Kegagalan Paling Sering (Common Failure Points AOS 10)

NTP Desynchronization (Clock Skew)

Jika jam AP selisih > 5 menit dari UTC, handshake TLS ke Activate atau Central otomatis di-drop (Certificate Date Invalid).

Unassigned License / Group

AP sudah muncul di GreenLake Inventory, tetapi belum di-assign Foundation License atau belum dimasukkan ke Group AOS 10.

AAA & Policy Security Architecture

802.1X, User Roles & ClearPass CPPM Integration

Prinsip Policy Enforcement Firewall (PEF) dan perbedaan pemrosesan autentikasi di AOS 8 vs AOS 10.

• Arsitektur AOS 8 (Controller-Centric)

Traffic client di-tunneling menggunakan GRE ke Mobility Controller. Controller bertindak sebagai RADIUS NAS Client yang berbicara langsung ke ClearPass.

  • Role ditentukan oleh atribut RADIUS: Aruba-User-Role.
  • Stateful Firewall PEF berjalan di tingkat Controller.
  • NAS-IP-Address yang tercatat di ClearPass adalah IP Controller.

• Arsitektur AOS 10 (Distributed Bridge Mode)

Jika mode Bridge (tanpa Gateway), AP bertindak langsung sebagai NAS Client ke ClearPass. Firewall PEF dieksekusi langsung di core CPU masing-masing AP.

  • ClearPass wajib mengizinkan subnet IP AP sebagai valid NAD Device (atau gunakan IP Gateway jika tunnel mode).
  • Cloud Guest Portal di-redirect via URL Central atau ClearPass Web-login.
  • User Role dikirim dari Central Cloud Group configuration.
Troubleshooting CLI Live Tracing

Decoder: `show auth-tracebuf`

Perintah paling penting di CLI Aruba untuk mengisolasi titik putus handshake EAP/RADIUS dalam hitungan detik.

# Jalankan filter MAC address client di controller:
(MC-01) # show auth-tracebuf mac 48:2a:e3:11:22:33
Tracebuf Event Analisa Kondisi Penyebab Masalah (Root Cause)
server-timeout Controller tidak menerima balasan RADIUS Access-Request. Firewall memblokir UDP 1812/1813, ClearPass service down, atau RADIUS Shared Secret mismatch.
eap-failure / rad-reject ClearPass menolak kredensial yang dikirim client. Password salah di AD, sertifikat EAP-TLS expired/untrusted, atau service policy di ClearPass tidak match.
client-timeout Client berhenti membalas EAP-Request dari Controller. Supplicant client menolak sertifikat ClearPass (prompt trust certificate di-cancel pengguna) atau RF drop.
eap-success Autentikasi 802.1X sukses, proses dilanjutkan ke 4-Way WPA Handshake. Normal. Jika client tetap tidak connect setelah ini, masalah berada pada DHCP VLAN atau Captive Portal.
Trap Lapangan RFC 3576 / Dynamic Auth

Konflik Port CoA / Disconnect-Request (UDP 3799 vs 5999)

Penyebab nomor satu mengapa fitur ClearPass Re-authentication, Disconnect, atau Quarantining gagal di Aruba Controller.

Aruba Legacy Default Port: UDP 5999

Secara historis, ArubaOS menggunakan port proprietary UDP 5999 untuk RFC 3576. Di ClearPass, saat menambahkan Network Device dengan Vendor Type Aruba, port CoA default sering kali terisi 5999.

IETF RFC Standard Port: UDP 3799

Standard RFC 3576 / RFC 5176 mendefinisikan port UDP 3799. Aruba Central Gateways dan ArubaOS modern umumnya mendengarkan (*listen*) di port 3799.

# Verifikasi statistik paket CoA yang diterima controller:
(MC-01) # show rfc3576 statistics
# Jika nilai "Bad Authenticator" bertambah: Shared Secret RFC 3576 tidak cocok!
# Jika statistik "Disconnect Requests" tidak bertambah sama sekali: Port salah (3799 vs 5999) atau firewall drop!
